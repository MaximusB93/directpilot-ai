## ТЗ №1 — ядро метрик (ревью пройдено)

Влито в `main` PR #142. Добавлено два файла, ни один существующий

(34 теста). Ничего в проекте на модуль пока не переключено — это отдельная
следующая задача.

Проверки: `python -m compileall -q backend/app index.py backend/index.py` —
чисто; `python -m pytest -q backend/tests` — 463 (429 старых + 34 новых);
`npm run build` — зелёный. Вручную сверено на числах кабинета Green Flow из ТЗ
(`cost=181054.15, clicks=959, conversions=13`): `cpa≈13927 ₽`, `cpc≈188.79 ₽`,
`cr≈1.36%`, сумма вкладов CPC/CR сходится с изменением CPA (расхождение ~1e-6 ₽
на float, требование ТЗ — 0.01 ₽).

Места, где пришлось принять решение за пределами буквального текста ТЗ
(в спецификации не зафиксировано явно):
- у метрики `cost` в разделе 4 ТЗ нет формулы значимости — принято
  `is_significant=False` всегда, `confidence` считается по кликам, как у
  «остальных» метрик.
- `confidence` для «метрик, не зависящих от конверсий» (включая `impressions`
  и `ctr`) считается по числу кликов — по буквальному тексту раздела 4, хотя
  для `impressions`/`ctr` логичнее было бы по числу показов.
- `empty_spend` получила опциональный keyword `baseline_cr: float | None`,
  хотя в сигнатуре из ТЗ его нет — без него правило «порог 3 / baseline_cr»
  из раздела 6 нечем было бы реализовать.
- `estimate_savings` для сегмента с известными `conversions` не имеет заданной
  в ТЗ формулы `confidence` (текст описывает только случай `conversions is
  None` → `low`) — использована та же таблица уверенности по числу конверсий,
  что и в `compare()`.

### Результат ревью

Проверено независимо от тестов исполнителя: сходимость декомпозиции на 2000
случайных наборах даёт худшую ошибку 3,4e-10 при допуске 0,01; `None` нигде не
превращается в `0`; пороги Пуассона совпадают с ориентирами ТЗ (10 -> 89%,
50 -> 40%, 200 -> 20%, 1000 -> 9%); окна корректны; на числах кабинета Green
Flow CPA/CPC/CR совпали с ТЗ.

Найден и исправлен один дефект: `estimate_savings` падала с `ZeroDivisionError`
на вырожденном периоде (`date_to` раньше `date_from`, `days == 0`), что
противоречило правилу раздела 1 ТЗ «ни одно деление не должно бросать
исключение». Добавлен guard и регрессионный тест.

Два пробела из списка выше — недоработки самой спецификации, не реализации:

- **значимость `cost` не определена в ТЗ.** Сейчас `is_significant=False`
  всегда, поэтому рост расхода в 10 раз помечается незначимым. Для утренней
  сводки это неверно: скачок расхода нужно показывать первым. Закрыть в ТЗ №3.
- **`confidence` для `impressions` и `ctr` считается по кликам**, хотя логичнее
  по показам. Исполнитель следовал букве раздела 4.

Следующий шаг (не в этой задаче): перевести
`campaign_dynamics_analyzer.py` и подобные сервисы на этот модуль.

## ТЗ №4 — гигиена интерфейса (ревью пройдено)

Влито в `main`. Изменения только в `src/**`, новых CSS-файлов
нет. Новый файл один: `src/core/labels.js` — общий словарь «код → название».

Что сделано по шести пунктам ТЗ:

1. Слипшиеся подписи. Одно базовое правило для шаблона
   `<article><span>Подпись</span><strong>Значение</strong></article>` в
   `app-product-polish.css`, а не правило на каждый контейнер. Проверено в
   браузере на реальных стилях: `.syncStatusGrid` и `.insightGrid` больше не
   слипаются, `.featureGrid` (нумерованные карточки) остался `inline`, селектор

   загрузки и ошибки везде прочерки, а не нули. При ошибке поверх ранее
   загруженных данных показывается пометка со временем загрузки. Подпись
   «Данные за период ещё не загружены» — только когда данных действительно нет.
3. «Оптимизация». Ярлык кнопки постоянный («Обновить план»), прогресс вынесен в
   отдельную строку. Строка прогресса живёт в отдельном значении, которое
   очищается в `onFinally`, поэтому индикатор не может пережить запрос ни при
   успехе, ни при ошибке.
4. Служебное `fix` / `ok` над заголовками убрано (два места, не одно:
   `renderSyncDiagnosticsPanel` и `renderYandexDirectAuditPanel`).
5. Совет остался в одном месте: строка «Фокус:» убрана, карточка готовности
   теперь описывает состояние, а действие называет только панель «Следующий
   шаг», одной формулировкой.
6. Коды. `labelFor` возвращает `null` для неизвестного кода, вызывающий код
   ставит прочерк или опускает строку — сырое значение не печатается нигде.
   Убраны все запасные варианты вида `словарь[code] || code`. UUID привязки
   аккаунта скрыт, периоды выводятся как «9 июня — 8 июля 2026».

## ТЗ №2 — долговечная история дневных данных (ревью пройдено)

Влито в `main`. Изменено три файла плюс новый тест:
`backend/app/models.py`, `backend/app/db.py`, `backend/app/services/client_sync.py`,
`backend/tests/test_daily_history.py` (16 тестов).
`campaign_dynamics_analyzer.py`, `ai_audit_jobs.py` и фронтенд не тронуты.

Что сделано по семи пунктам ТЗ:

1. Уникальность `(client_id, stat_date, campaign_id)` — в модели
   (`__table_args__`, работает для новых баз и для SQLite в тестах) и аддитивным
   `CREATE UNIQUE INDEX IF NOT EXISTS` в `ensure_mvp_schema` для существующих.
   Перед индексом выполняется чистка дубликатов, оставляющая строку с
   наибольшим `loaded_at`; без неё создание индекса на боевой базе упало бы и
   прервало весь патч. Обе SQL-строки вынесены в именованные константы
   `DAILY_STATS_DEDUPLICATE_SQL` / `DAILY_STATS_UNIQUE_INDEX_SQL`, поэтому тест
   проверяет ровно тот SQL, который выполняется в продакшене.
2. Upsert вместо «удалить диапазон → вставить». Диапазонного удаления больше
   нет. `loaded_at` обновляется при каждом upsert. Строка, которой нет в новом
   отчёте, не удаляется.
3. Удаление истории при ошибках подключения убрано в обеих ветках. Удаления
   `DirectCampaignPeriodStat` и `DirectSearchQueryPeriodStat` там же оставлены.
4. Первичная загрузка: 400 дней частями по 90, от свежих к старым, каждая часть
   отдельной транзакцией.
5. Инкрементальная синхронизация: окно доуточнения 21 день + пропущенные дни
   между `MAX(stat_date)` и вчера. Признак «нужна первичная загрузка» —
   `MIN`/`MAX(stat_date)`, отдельного поля состояния нет.
6. `days=min(max(days, 30), 30)` убран, параметр работает.
7. Данные по сроку давности не удаляются.

Проверки: `python -m compileall -q backend/app index.py backend/index.py` —
чисто; `python -m pytest -q backend/tests` — 480 (464 существующих + 16 новых),
ни один существующий тест не правился; `npm run build` — зелёный.

Отдельно проверено, что PostgreSQL-ветка upsert компилируется в ожидаемый
`ON CONFLICT (client_id, stat_date, campaign_id) DO UPDATE ... loaded_at = now()`:
тесты идут на SQLite, а продакшен — на PostgreSQL, и эта ветка кода тестами
не покрывается.

Решения за пределами буквального текста ТЗ:

- **Upsert реализован для двух диалектов.** PostgreSQL и SQLite поддерживают
  одинаковый `ON CONFLICT ... DO UPDATE`; для прочих диалектов оставлен
  переносимый путь «найти и обновить», чтобы функция не падала.
- **Дедупликация внутри одного отчёта.** Директ может вернуть один и тот же
  день и кампанию дважды, а PostgreSQL не даёт одному `ON CONFLICT` изменить
  строку дважды («cannot affect row a second time»). Батч схлопывается до
  последнего вхождения ключа перед вставкой.
- **`sync_campaign_daily_stats` теперь коммитит.** Это требование пункта 4
  (часть = транзакция). Побочный эффект: к моменту вызова уже записанные
  `DirectCampaignPeriodStat` фиксируются раньше, чем раньше. Поведение при
  ошибке не изменилось — прежний обработчик тоже коммитил их вместе со
  статусом ошибки.

Известное ограничение, зафиксировано тестом `test_old_interior_hole_is_left_alone`:
дыра в истории **старше** и `MAX(stat_date)`, и окна доуточнения, сама не
залечивается. Это прямое следствие формулировки пункта 5 («пропущенные дни между
`MAX(stat_date)` и вчера») и правила «дни старше окна доуточнения считаются
окончательными». Такая дыра может возникнуть, если Директ однажды не отдал часть
диапазона внутри чанка. Если это нежелательно, дешёвое исправление — искать
пропуски по всей истории (это ~400 строк на клиента, один `SELECT DISTINCT`), но
это расширение границ ТЗ, поэтому не сделано.

Ручная проверка на кабинете Green Flow (два запуска подряд, диапазоны запросов и
`MIN`/`MAX`/`COUNT`) не выполнялась: нужен живой доступ к Директу.

## Незакрытые вопросы

- **Дыры в истории старше окна доуточнения не лечатся.** Планировщик ищет
  пропущенные дни только между `MAX(stat_date)` и вчера, поэтому пропуск внутри
  уже загруженного диапазона — если Директ однажды не отдал часть чанка —
  останется навсегда. Поведение зафиксировано тестом
  `test_old_interior_hole_is_left_alone`, то есть это осознанный выбор в
  границах ТЗ №2, а не случайность. Дешёвое исправление: искать пропуски по всей
  истории одним `SELECT DISTINCT` (порядка 400 строк на клиента).
- **Расхождение словаря и кодов бэкенда.** `src/core/labels.js` не показывает
  неизвестный код вместо того, чтобы печатать его сырым, — экран не ломается,
  но подпись молча пропадает, и заметить это трудно. Нужен тест, сверяющий
  ключи словаря с кодами, которые реально отдаёт бэкенд. Найдено при
  реализации ТЗ №4.
- **Разрезать `ai_audit_jobs.py`** (9 501 строка, 228 функций верхнего уровня)
  на 6–8 модулей. Обязательно перед задачами 5 и 6. Отдельное ТЗ не написано.
- **Фоновое выполнение аудита.** 915-секундный аудит выполняется цепочкой
  запросов из браузера, потому что у Vercel нет фонового процесса. Блокирует
  этап 3 (аудит по расписанию) и всё, что после.
- **Учёт расхода на ИИ и дневной лимит.** Один аудит — 88 011 токенов промпта.
  Ни лимитов, ни квот, ни учёта. Полдня работы, не запланировано.
- **Незаконченный переезд фронтенда.** Модули страниц вынесены, но не
  подключены: в каждом лежит записка `nextStep: подключить ... к ...Content`.
  Решить на этапе 0: доводить или откатывать.
- **Модель атрибуции** не передаётся в отчёты и не показывается пользователю.
  Все выводы по CPA содержат скрытое допущение.
