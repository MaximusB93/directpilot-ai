# ТЗ №3. Утренняя сводка

Полоса **A**. Ветка `feat/morning-digest` от `main`.

## Зачем

Первый из пяти режимов продукта, который работает без участия человека. Каждое утро
система сама смотрит вчерашний день по всем кабинетам и приносит от нуля до пяти
изменений, каждое — с числами и одним действием.

Это то, ради чего строились две предыдущие задачи: `metrics_core` даёт окна,
декомпозицию и значимость, история из ТЗ №2 даёт глубину для сравнения.

## Границы задачи

**Делаем:** расчёт сводки, хранение, endpoint, планировщик. Только backend.

**Не делаем в этой задаче:**

- не делаем экран сводки — это отдельное ТЗ полосы B;
- не трогаем `ai_audit_jobs.py` и аудит;
- не переводим `campaign_dynamics_analyzer.py` на `metrics_core` — он остаётся как есть,
  сводка его не использует и не заменяет;
- не зовём Яндекс.Директ: сводка считается по уже сохранённым дневным данным;
- не зовём языковую модель. Сводка целиком детерминированная. Объяснение текстом —
  задача следующего этапа, и она будет надстройкой над готовыми фактами.

Последнее — принципиально. Если сводку писать моделью, она снова начнёт говорить общо.
Числа, пороги и выводы считает код; модель потом лишь пересказывает то, что уже посчитано.

## Часть 1. Закрыть два пробела в `metrics_core`

Оба выявлены при реализации ТЗ №1 и записаны в `docs/state.md`. Это недоработки
спецификации, а не реализации.

### 1.1. Значимость расхода

Сейчас `compare()` всегда возвращает `is_significant=False` для `cost`, поэтому рост
расхода в десять раз помечается незначимым. Для утренней сводки это прямая ошибка:
скачок расхода — первое, что нужно показывать.

Причина пробела в том, что к расходу неприменима та же логика, что к конверсиям.
Конверсии — счётная величина с шумом выборки, и вопрос «настоящее ли это изменение».
Расход измерен точно, шума выборки в нём нет. Вопрос другой: **существенно ли изменение**.

Правило: `cost` значим, когда изменение превышает и относительный, и абсолютный порог.

```
is_significant = abs(percent) >= COST_MATERIALITY_PCT  и
                 abs(absolute) >= COST_MATERIALITY_ABS
```

Значения по умолчанию: `COST_MATERIALITY_PCT = 20`, `COST_MATERIALITY_ABS = 1000` (рублей
за сравниваемое окно). Оба — именованные константы модуля.

Двойной порог нужен, чтобы рост с 50 ₽ до 150 ₽ не считался событием: относительно это
200 %, по существу — ничего.

`confidence` для `cost` оставить по кликам, как сейчас.

### 1.2. Основание уверенности для показов и CTR

Сейчас `confidence` для `impressions` и `ctr` считается по числу кликов. Логичнее по
числу показов: это их собственный знаменатель.

Ввести `_confidence_by_impressions` с порогами: `high` при 50 000, `medium` при 10 000,
`low` при 1 000, иначе `insufficient`. Применить к `impressions` и `ctr`.

Остальные метрики не трогать.

### 1.3. Тесты к части 1

- Рост расхода на 900 % при абсолютной разнице выше порога — значим.
- Рост со 50 ₽ до 150 ₽ — не значим (не пройден абсолютный порог).
- Рост на 5 % при большой абсолютной разнице — не значим (не пройден относительный порог).
- `confidence` для `impressions` при 60 000 показов и 100 кликах — `high`, а не `insufficient`.
- Существующие тесты `metrics_core` не ломаются.

## Часть 2. Расчёт сводки

Новый модуль `backend/app/services/morning_digest.py`.

### Входные данные

Только уже сохранённое: `DirectCampaignDailyStat` за нужные окна, `ClientAccount`
(целевой CPA), при наличии — бизнес-контекст. Никаких обращений к Яндексу.

### Окна

Из `build_windows(reference_date)`, где `reference_date` — вчера:

- **дневное сравнение:** `yesterday` против `same_weekday_prev_week`;
- **недельное подтверждение:** `last7` против `previous7`.

Дневной сигнал, не подтверждённый недельным окном, получает пониженную уверенность.
Дневных данных мало по определению, и без подтверждения тенденцией сводка начнёт
реагировать на случайные всплески.

### Сигналы

Шесть, каждый считается по кампании и по аккаунту целиком.

| Сигнал | Условие |
|---|---|
| `spend_spike` | `cost` значим по правилу 1.1 и вырос |
| `spend_drop` | `cost` значим по правилу 1.1 и упал |
| `cpa_growth` | `cpa` значим, вырос, и при заданном `target_cpa` превышает его |
| `conversions_drop` | `conversions` значим и упал, при этом `cost` не упал |
| `empty_spend_appeared` | кампания в `empty_spend` с `reliable=True`, которой не было в предыдущем окне |
| `ctr_collapse` | `ctr` значим по биному и упал |

Отдельно: `campaign_stopped` — были показы в предыдущем окне, вчера ноль. Это не
изменение метрики, а исчезновение объекта, поэтому проверяется отдельно от `compare()`.

### Содержимое находки

```python
@dataclass(frozen=True)
class DigestFinding:
    signal: str                  # один из перечисленных выше
    scope: str                   # "account" | "campaign"
    campaign_id: str | None
    campaign_name: str | None
    lever: str                   # "empty_spend" | "cpc" | "cr" | "unknown"
    evidence: dict[str, float | None]   # только числа, посчитанные кодом
    money_at_stake: float | None        # рублей в месяц
    confidence: str              # из metrics_core
    confirmed_by_week: bool
    action: str                  # одно конкретное действие
```

**Рычаг** для `cpa_growth` определяется через `decompose_cpa`: `dominant_factor`
переносится в `lever` напрямую. Для `empty_spend_appeared` рычаг всегда `empty_spend`.
Для остальных — `unknown`, если декомпозиция неприменима.

**Деньги** считаются через `estimate_savings` для пустого расхода и как
`(cpa_current - cpa_previous) * conversions_current`, приведённое к 30 дням, для роста CPA.
Если посчитать нечем — `None`, но тогда находка не попадает в сводку вовсе
(см. правило отбора).

**Действие** — строка из фиксированного набора шаблонов, по одному на сигнал и рычаг.
Не свободный текст: набор шаблонов проверяется тестом.

### Правила отбора

1. Находка без `money_at_stake` не показывается. Нельзя просить внимания, не назвав цену.
2. Находки сортируются по `money_at_stake` по убыванию.
3. В сводку попадает не более **пяти**.
4. Находка уровня аккаунта имеет приоритет над находкой по кампании при равных деньгах.
5. Если после отбора не осталось ничего — сводка пустая, и это **успешный результат**,
   а не ошибка. Пустая сводка сохраняется наравне с непустой.

Молчание — обязательное свойство. Сводка, которая срабатывает каждый день, перестаёт
читаться через неделю, и тогда пропущенной окажется та единственная, что была важна.

### Подавление повторов

Находка с той же тройкой `(client_id, campaign_id, signal)`, уже показанная за последние
**7 дней**, помечается `repeated=True` и не занимает одно из пяти мест, пока есть
неповторяющиеся находки. Если новых нет — повторы показываются, но помеченными.

Без этого «высокий CPA в кампании X» будет приходить семь дней подряд одинаковым текстом.

## Часть 3. Хранение

Новая таблица `morning_digests`:

| Колонка | Назначение |
|---|---|
| `id` | uuid |
| `client_id` | клиент |
| `digest_date` | дата сводки (вчерашний день) |
| `created_at` | когда посчитана |
| `findings_json` | сериализованный список находок |
| `findings_count` | для быстрых выборок |
| `status` | `ok` \| `no_data` |

Уникальность по `(client_id, digest_date)`. Пересчёт за тот же день перезаписывает запись.

Схему менять только аддитивно, как требует `PROJECT_PLAN.md`, раздел 7:
`CREATE TABLE IF NOT EXISTS` в `ensure_mvp_schema`, по образцу уже имеющихся там таблиц.

`status = "no_data"` — когда за нужные окна нет дневных строк вообще. Это отличается
от пустой сводки: там данные есть и всё спокойно, здесь данных нет и сравнивать нечем.
Смешивать эти состояния нельзя — по той же причине, по которой `None` не равно нулю.

## Часть 4. Endpoint

```
POST {api_prefix}/digests/run
GET  {api_prefix}/clients/{client_id}/digest?date=YYYY-MM-DD
```

`POST /digests/run` считает сводки. Параметры тела: необязательный `client_id`
(тогда только он), необязательный `digest_date` (по умолчанию вчера).

**Аутентификация.** Запуск дёргает планировщик, у которого нет пользовательской сессии.
Проверять общий секрет из переменной окружения `DIGEST_CRON_SECRET`, передаваемый
заголовком `Authorization: Bearer <секрет>`. Если переменная не задана — endpoint
отвечает 503 и ничего не считает: незащищённый запуск недопустим, потому что он
доступен всему интернету.

`GET .../digest` — обычный пользовательский endpoint под текущей сессией, со всеми
проверками принадлежности клиента организации, как в остальных роутерах.

**Бюджет времени.** Обработка идёт по клиентам последовательно. Перед каждым следующим
клиентом проверяется, что до мягкого предела в **45 секунд** остаётся время; если нет,
обработка прекращается и в ответе возвращается, сколько клиентов обработано и сколько
осталось. Функция на бессерверной платформе ограничена по времени, и молчаливый обрыв
на середине хуже честного частичного результата.

Повторный запуск за тот же день безопасен: уже посчитанные клиенты пересчитываются
и перезаписываются, недосчитанные досчитываются.

## Часть 5. Планировщик

Здесь есть неопределённость, которую надо разрешить проверкой, а не предположением.

Оба `vercel.json` в проекте написаны в старом формате (`"version": 2` с `builds` и
`routes`). Поддержка свойства `crons` в этом формате не гарантирована.

**Порядок действий:**

1. Попробовать добавить `crons` в `backend/vercel.json` — раз в сутки, `POST /digests/run`.
2. **Проверить на превью-развёртывании, что задание действительно зарегистрировалось.**
   Не «добавили конфиг — значит работает».
3. Если не регистрируется — не переписывать формат `vercel.json` в рамках этой задачи
   (это отдельный риск для деплоя). Вместо этого добавить запланированный workflow
   GitHub Actions: `schedule` раз в сутки, один шаг `curl` на endpoint с секретом
   из secrets репозитория.

Второй вариант не хуже первого: он не зависит от хостинга, виден в истории запусков и
использует инфраструктуру, которая в проекте уже есть.

Что бы ни выбралось, **endpoint не должен знать, кто его вызвал**. Единственное
требование к вызывающему — правильный секрет.

## Тесты

Новый файл `backend/tests/test_morning_digest.py`. Обязательное покрытие:

1. Спокойный день без изменений даёт **пустую сводку со статусом `ok`**, а не ошибку.
2. Отсутствие дневных данных даёт статус `no_data`, и это отличается от пункта 1.
3. Скачок расхода выше обоих порогов попадает в сводку; рост с 50 ₽ до 150 ₽ — нет.
4. Рост CPA раскладывается: при неизменном CR рычаг `cpc`, при неизменном CPC — `cr`.
5. Находка без `money_at_stake` не попадает в сводку.
6. В сводке не больше пяти находок, отсортированных по деньгам по убыванию.
7. Повтор той же тройки за последние 7 дней помечается `repeated` и уступает место новой.
8. Если новых находок нет, повторы всё же показываются.
9. Дневной сигнал без подтверждения недельным окном имеет пониженную уверенность.
10. `campaign_stopped` срабатывает, когда показы были и исчезли.
11. Повторный запуск за тот же день перезаписывает запись, а не создаёт вторую.
12. `POST /digests/run` без секрета — 401; при незаданной переменной окружения — 503.
13. `GET .../digest` не отдаёт сводку клиента чужой организации.
14. Бюджет времени: при исчерпании возвращается частичный результат с числом
    необработанных клиентов, а не исключение.
15. Расчёт не обращается к сети — проверяется тем, что тест проходит без подмены
    коннектора Яндекса.
